# Team gateway deployment checklist

Review this list before giving teammates access to a CliRelay deployment. Protocol compatibility is a tested subset of each provider, model and client combination, not a promise that every OpenAI, Claude or Gemini feature works identically.

## Access and credentials

- Keep upstream provider credentials separate from client-facing gateway API keys. Give each person or integration its own gateway key with the necessary model, channel, tenant and quota restrictions.
- Keep `allow-unauthenticated: false`. Verify that a request to a client API without a key is rejected before publishing its URL.
- Treat generated installation secrets as real credentials. Replace any key that was shared, copied into an example or exposed. Create a replacement gateway key, update and verify clients, then revoke the old key and verify that it is rejected. Revoke immediately when compromise is suspected.
- Expose only the client API paths you need, such as `/v1/*` or `/v1beta/*`. Put `/manage`, `/management.html` and `/v0/management/*` behind a VPN, private network or reverse-proxy IP allowlist. A login page does not prove that backend APIs are protected.
- Test sensitive management endpoints without credentials from an external connection. They must not return configuration or auth files. Valid access still requires backend management authorization; network restrictions are an additional boundary.
- Configure `trusted-proxies` only for the proxies you operate and ensure they replace client-supplied forwarding headers. Setting a trusted proxy does not authorize remote management; `remote-management.allow-remote` remains a separate policy. A TCP relay cannot always be distinguished from a local HTTP client, so retain the network boundary.

## Compatibility and logs

- Before rollout, test the actual client and model with non-streaming and streaming requests, tool calls and results, namespace/MCP tools when used, reasoning settings, provider-specific headers and model aliases. Test cancellation, rate limits and failover too.
- Request metadata can identify keys, accounts, models, routes, status, timings and usage. Restrict who can read it and include it in the backup/retention policy.
- `request-log-storage.store-content` controls database storage of full request/response bodies and defaults to `false`. `content-retention-days` and `max-total-size-mb` bound stored bodies; zero disables the corresponding limit. Lightweight metadata has separate retention behavior.
- File request logging is a separate surface. Audit both file and database settings, including error logs, before sending proprietary source or personal data. Do not publish config exports, auth files, raw bodies or credential-bearing logs in issues.
- Back up PostgreSQL, configuration and credentials securely, and rehearse restoration before upgrades. Record the deployed backend and panel versions to make regressions reproducible.

## Slow disks and Synology NAS

The application runs as `10001:10001`. Ensure this user can access the `auths`, `logs` and `data` mounts and read `config.yaml`; saving configuration also requires write access. Synology/DSM ACLs may prevent the entrypoint from repairing ownership. Adjust the host ACL/ownership for the actual mounts, instead of broadening permissions to everyone.

PostgreSQL runtime migrations accept `CLIRELAY_MIGRATION_TIMEOUT`, a positive Go duration such as `120s` or `5m`; the default is `30s`. Pass the variable to the application process. For Compose, add an override and verify the resolved configuration before restarting:

```yaml
# compose.override.yaml
services:
  cli-proxy-api:
    environment:
      CLIRELAY_MIGRATION_TIMEOUT: "5m"
```

This setting covers runtime migrations, not every startup operation or configuration-store bootstrap. If startup still times out, identify the failing stage from the sanitized error before increasing unrelated timeouts.

A dirty migration requires a backup and inspection of the schema against the exact migration SQL and checksum for the installed version. Do not only clear `dirty`, blindly replay SQL, change checksums or delete the data volume. A timeout may occur before or after the SQL commits. Keep PostgreSQL `fsync`, `synchronous_commit` and `full_page_writes` enabled; disabling durability is not the supported fix for slow storage.

`CLIRELAY_ADMIN_PASSWORD` bootstraps the first admin in an empty database and is generated by the standard installation flow. Changing it does not rotate an existing administrator's password. The updater sidecar intentionally disables the application image's inherited healthcheck; it must not probe a nonexistent local application port or borrow another container's health as proof of its own.

## Word guard switch

The word guard checks every request against the platform, tenant and API key word policies before an account is chosen. It reads its policies from the database with a short time limit (75 ms): when the database does not answer in time, the request continues with the policies the guard last saw, or unchecked if it has seen none. If the guard itself misbehaves, set `CLIRELAY_WORD_GUARD=off` for the application process and restart: no request is checked and no reply is filtered until the variable is removed. Any other value, including a typo, leaves the guard on. The state is logged at start (`word guard is switched off by CLIRELAY_WORD_GUARD`).
